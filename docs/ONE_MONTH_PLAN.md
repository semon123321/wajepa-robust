# 四周交付与面试准备

目标：在一台 RTX 5070 Laptop 8GB 上完成可复核的近期论文适配项目，并能
独立解释实现、实验与限制。当前已经完成官方权重推理、真实数据接入、
两类适配训练、对照/消融和小规模独立日志评估。性能收益尚不足以称为核心突破。

## 第一周：理解已实现部分，核查数据与训练

每天约 2–3 小时阅读与修改，比只运行脚本更重要。

- 阅读 WA-JEPA 原文，手推其 flow 采样与联合世界/动作依赖；对照
  `_encode_scene_context`、`predict_trajectory` 和本项目动作蒸馏实现。
- 运行公开适配器和锁定 token 测试；挑 3 个成功、3 个失败场景，解释
  输入故障如何改变输出。全部场景结果仍要保留。
- 阅读 NAVSIM 的 Scene、坐标系、官方场景 filter，确认当前独立日志数。
- 学会看 CUDA 计时和显存，明确为什么缓存编码器、为什么冻结主干。
- 拿一个你自己提出的故障，例如 0.5 秒左右变动延迟，写成可测试代码。

交付：5 分钟项目讲解、模型结构图、一次自己完成的可复现实验。

## 第二周：增加训练多样性，改善任务对齐

现有更多 mini 分片已下载，可以扩展到多个独立日志。小 adapter 的计算
不重，但生成全部缓存需要时间与磁盘：有动作教师缓存约每场景 106MB。

1. 新建版本化的训练 manifest，优先增加日志多样性和转弯/交互场景，
   避免靠大量重叠直行片段增加表面样本数。选样依据不能是测试误差。
2. 用同一份缓存比较 context-only / action-only / combined loss；原始
   dev_v1 和 dev_v2 数据规模不同，不是严格的目标函数消融。
3. 从训练与验证日志里选目标权重，使用三个训练种子；冻结方案后再测试。
4. 研究冻结 teacher 的动作一致性为何有时过弱：teacher 准确性上限、
   当前按单步蒸馏与完整 rollout 差别、动作/世界损失对上下文的梯度。
5. 连续帧龄优势目前没有成立；若二值状态同样好，就保留这个结论。

交付：相同数据/预算的目标消融表、三个种子的均值和方差、负面结果分析。

## 第三周：规划评分与泛化

- 接入官方 NAVSIM v2.2 scorer 与 nuPlan maps。建议使用独立 CPU 评分环境，
  通过已保存预测评估，避免官方旧版 torch/numpy要求覆盖 Blackwell 环境。
- 使用官方实现并注明是否仅运行第一阶段、是否缺少合成后续场景。
  只有完整执行相应协议才报告对应 EPDMS；部分指标单独标明。
- 报告碰撞、可行驶区域、进度等官方组件，检查 ADE 改善是否伴随规划收益。
- 把多相机同时故障、无元数据、未见过的延迟模式作为独立泛化实验。
- 配对比较按原始日志做统计。目标至少 10 份独立评估日志，当前仅 4 份。

交付：官方评分的可运行脚本和真实结果；泛化/速度/显存表。

## 第四周：冻结与面试

- 冻结模型、版本和所有选择规则；重新测试固定 manifest，发布 tag。
- README 首页用一张表说明：原模型、简单方法、你的改进、失败条件。
- 准备真实相机与轨迹演示、5 分钟讲解和 15 分钟技术追问。
- 练习解释 PyTorch 梯度、混合精度、坐标变换、attention、EMA、flow matching、
  表征重建与规划目标的区别。能现场改一个小功能并验证它。
- 简历只写已完成内容；性能数字必须附上评估规模、指标、条件与对照。

## 优先级

最值得补的两项是 **独立日志上可靠的规划收益** 和 **你对代码/论文的独立理解**。
完整预训练、视频像素生成、大规模 RL、分布式 Scaling 在本次一个月与单卡
约束下不列为交付承诺。可以解释它们与项目的关系，不能写成已有经验。
